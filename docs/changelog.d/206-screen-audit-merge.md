- **The two geometry guards became one walk of each screen** (IMPROVE-9). `OverflowAuditUITests` asked *is anything drawn outside the screen?* and `TypeSqueezeUITests` asked *is a sentence squeezed into a column by the control beside it?* — two questions, but the same nine screens, the same launch at Accessibility XL and, in six cases, the same screen launched twice. They were separate only because the pull requests that introduced them could not be stacked. `ScreenAuditUITests` now launches each screen **once** and asks both questions of it. That costs build-machine time rather than saving it — 198 seconds became 270 on an iPhone 16 Pro, about +36 per cent — because the overflow question now gets the walk it never had. The first draft of this entry claimed the opposite, on the reasoning that six fewer app launches must be cheaper; the launch was never the dominant cost, the walk is, and the honest figure arrived only after someone timed both suites on the same device. It read 485 seconds before three measured fixes brought it to 270. Merging them also fixed the weaker half — the overflow guard measured a single viewport, so on a long screen it only ever audited the top of it, while the squeeze guard already knew the bug lives below the fold (at Accessibility XL a Settings row is about 190 points tall, so the first *“Asks before …”* note is the sixth row). Both questions are now asked of every state the walk realises, and the walk **goes back up**: a test that only ever scrolls one way leaves the screen somewhere it did not start and never sees a layout in the order a person scrolling back sees it. Verified the way a guard has to be — by breaking the app on purpose and watching each half name the defect, with its numbers.
